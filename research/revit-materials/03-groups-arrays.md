# Group、Array 与幕墙系统：规则重复构件的高效做法与风险

## 适用场景

- 本文用于重复房间、卫生间组合、典型家具布置、规则座位、立面格栅和幕墙单元。
- 关键不是“复制得多快”，而是选择一种能在后期改型、统计和出图时不失控的重复机制。
- Revit 中 Group、Array、嵌套族和 Curtain Wall 都能制造重复，但它们的修改成本截然不同。

## 先按重复对象分流

1. 重复的是一套多类别空间布置，且各套之间基本完全相同：考虑 Model Group。
2. 重复的是一个单一构件，尺寸/数量/间距有规则：考虑 Array 或参数化族。
3. 重复的是连续立面网格、竖梃与面板：优先 Curtain Wall 系统。
4. 重复的是可跨项目调用的标准产品：优先 Loadable Family 的类型与复制。
5. 重复对象需独立统计时，避免把它埋在不可共享的嵌套数组里。[S1][S2]

## Group：适合“同一套”，不适合“相似但不同”

- Model Group 把多种模型元素作为一个可重复单元，适合标准客房、卫生间核心、重复户型家具布置。
- 成功前提是每一套的墙、门、家具和设备确实可同步变更。
- Group 的收益来自“编辑组定义，所有实例跟随”，而不是单纯复制。
- 将一个典型房间先做完整，再组化；在组化前清理不必要的独立标高、文字和临时线。
- 组内元素若频繁需要单独改，会迫使用户排除/变体，迅速削弱组的价值。
- 当各户型只看似相同、但墙洞、家具、标注或面积都不同，应改用复制基础模型加少量族类型。
- Detail Group 可服务于重复二维注释，但必须与对应模型变更的责任边界清楚。

## Group 的方法步骤

1. 先完成一套典型单元的主体与必要家具。
2. 把可共享的模型元素纳入组，排除临时辅助几何和一次性表现物。
3. 命名按用途和版本，例如 `A户型_卫浴核心_V1`。
4. 复制组实例到对应位置，并立即检查宿主、标高、镜像与房间边界。
5. 后续修改先判断是“所有实例都应改”还是“只有此处例外”。
6. 全局改时进入组编辑；单点例外时先评估是否应取消该处组关系。
7. 每次大改后检查组实例数量、警告和图纸中的标注关系。

## Group 的风险

- 组内外存在复杂宿主、约束或相互依赖时，编辑容易产生错误或无法完成的修改。
- 反复“排除组元素”会造成同名组实例实际内容不同，审查难度上升。
- 将门窗、墙和房间边界塞进大量变体组，后期平面变动成本很高。
- 组不应替代真正的标准族库；家具本体仍应是正确类别的 Loadable Family。
- 标注并不天然随模型组同步；需要通过视图策略或 Detail Group 进行单独管理。

## Array：参数化前先问能否被统计

- Array 适合规则重复：固定数量、固定间距、最后一项定位、沿直线或弧线的构件。
- 对象是标准的椅子、灯具、百叶或格栅时，先确保原对象是正确类别的单件族。
- 项目中 Array 可快速布置，但复杂阵列会使局部编辑、统计和宿主关系变脆弱。
- 族内 Array 可用数量参数控制，但应限制极值并充分 flex。
- Autodesk 论坛案例表明，族内阵列对象在项目明细表的计数可能只表现为“阵列父族”，而不是内部每一件。[S1]
- 若每个重复件都必须出现在明细表中，优先放置独立实例，或使用共享嵌套并实测明细结果。[S1][S2]

## 项目 Array 的工作规则

1. 先放一个经过验证的单件族。
2. 明确控制规则：固定数量、固定间距或最后一项位置；不要在同一阵列中混淆。
3. 先以小数量测试复制、旋转、镜像和删除的行为。
4. 为阵列提供稳定的参照线、墙面、标高或工作平面。
5. 完成后创建临时明细表，核实数量、类型、宿主和参数。
6. 如开始出现大量局部例外，撤销阵列思路，改为单件族/系统格网。

## 族内 Array 的工作规则

- 用参照平面定义第一件、最后一件和总体宽度，阵列对象全部锁在骨架上。
- 数量参数应有合理下限；例如 1 或 2，而不是允许 0/负数导致失败。
- 阵列与公式一起使用时，逐个测试数量、总长和最小间距。
- 用实例控制数量只在每个放置位置确需不同数量时采用；否则类型参数更易管理。
- 如果内部构件必须计量，查明共享设置与明细类别，不以视觉重复推断表中数量。[S1][S2]

## 幕墙系统：立面规则优先于对象复制

- 连续玻璃立面、有规则网格/竖梃/嵌板的对象，Curtain Wall 是首选系统。[S3]
- 网格是规则，竖梃和嵌板是规则的结果；先建立格网逻辑，再微调特殊区域。
- 典型流程：墙类型 → 垂直/水平网格规则 → 竖梃类型 → 面板类型 → 门/特殊面板替换。
- 固定距离适合模数明确的分格；固定数量适合总宽变化时保持视觉节奏的分格。
- 面板若有独特几何、材料或信息，做 Curtain Panel Family，而不是用普通 Generic Model 贴在玻璃上。
- 竖梃截面适合用正确用途的 Profile Family；Profile Usage 能限制它在对应构件中出现。[S3]

## 幕墙的例外处理

- 先完成典型区，再单独处理门区、转角、错层、收边和不规则面板。
- 门区替换为 Curtain Wall Door 或相应面板族，避免删掉格网后再手工补玻璃。
- 特殊大面板应作为类型变体，不要在每一处手工改材质/尺寸。
- 复杂立面若网格规则连续，宁可用少数类型和局部 Override，也不要拆成大量独立墙。
- 若每块面板都不同、且几何由自由曲面驱动，先研究 Mass/自适应族；不要强塞进标准幕墙。

## Group、Array、幕墙的选择矩阵

- “一间重复卫生间”：Group，前提是其差异极少。
- “20 把同型椅子”：独立族实例或轻量项目 Array，取决于是否要局部调整和统计。
- “可变长度长桌的一排桌腿”：族内 Array，但先测试数量公式和明细行为。[S2]
- “规则玻璃幕墙”：Curtain Wall。
- “每层相同遮阳格栅”：可载入格栅族/面板族或 Curtain Wall；看它是否连续成系统。
- “每层近似但洞口不同的户型”：复制基础模型加类型控制，而不是强行 Group。

## 优点

- Group 将真正相同的复合单元集中维护。
- Array 将可量化的数量和间距显式化，避免手工等距失误。
- Curtain Wall 将立面模数、竖梃、面板和门区保留为可编辑系统。
- 正确的重复策略可减少修改次数，也能提升明细表可靠性。

## 风险与坑

- 可见的阵列数量不等于明细表中的可计数量；必须实际验证。[S1]
- 共享嵌套会影响项目中对象与明细的行为，设置前先明确统计要求。[S2]
- Group 中的例外持续增加时，会形成隐蔽变体，不如拆组后清晰。
- 用独立玻璃墙模拟幕墙会丢失网格、竖梃与面板类型的批量控制。
- 过度阵列化会使选择、宿主调整和图纸修改困难。

## 不适用情况

- 不规则的艺术安装、渐变布局或每件都不同的家具，不适合 Group/规则 Array。
- 需要逐个编码、逐个改材质、逐个移动的对象不适合被复杂阵列封装。
- 不连续、没有格网关系的玻璃构件不应为了“看起来高级”做成幕墙。

## 课程作业建议

- 先在一个小测试区验证 Group/Array/幕墙的修改和统计，再复制到全项目。
- 作业中 Group 数量应少而明确；典型卫生间和重复客房通常已足够。
- 重要的家具、门窗和幕墙面板，用明细表抽查数量，别只看三维视图。
- 立面先用 Curtain Wall 做 80% 典型规则，剩余 20% 用局部替换解决。
- 最后一天禁止把已稳定的成片独立构件强制 regroup；变更风险高于节省的点击。

## 交付前快速检查

- 选中一个组实例，确认编辑组不会意外改变例外房间。
- 选中一组阵列，确认删改一件时对其他实例的影响符合预期。
- 打开相关明细表，核对可见数量与计划数量是否相符。
- 检查幕墙典型格、边缘格、转角格和门区各至少一处。
- 在平面、立面、剖面和三维中检查竖梃与面板的可见性。
- 修改一个面板类型，确认不应变化的特殊面板没有被连带替换。
- 检查复制/镜像后门的开启方向和栏杆的扶手方向。
- 清除为了测试留下的临时阵列和无用组类型。
- 用一致的名称表达用途、模数和版本，避免“Group 1”“Array 2”。
- 若无法说明一个重复机制的维护边界，先用更简单的独立实例。
- 记录特殊规则，以便教师审阅或下一位编辑者接手。
- 输出 PDF 前在一张典型图纸验证线型、比例和图例表达。
- 把数据统计作为模型检查的一部分，而不是最后附加的表格工作。
- 保持一个可回退的版本，再执行整面幕墙或整层组的批量替换。
- 遇到异常计数时回到对象类别、共享设置和明细表字段三处排查。
- 把真正可复用的规律固化为类型，把一次性例外保留为明确例外。
- 这比追求“所有对象都在一个组里”更符合可维护 BIM 模型的目标。
