# 极简建筑 AI 团队架构

## 1. 架构结论

本工作区采用一个用户、一个轻量 Director 与五个专业 Agent 的极简架构。

用户是设计总监与最终决策者。

Director 只负责路由、Handoff、Gate 与项目事实源。

专业 Agent 分别负责概念、方案、Revit 图纸、可视化与汇报表达。

团队不再使用旧 8 Agent 与 3 Squad 作为当前运行结构。

旧角色内容仍保留在 `prompts/`，作为方法论归档和继承来源。

## 2. 组织图

```text
Human / 用户（设计总监，最终决策权）
└── 建筑设计总监（Director，轻量 Leader）
    ├── Concept Design Agent
    ├── Scheme Design Agent
    ├── Drawing Production Agent
    ├── Visualization Agent
    └── Presentation Agent
```

Director 不位于用户之上。

Director 是用户与专业 Agent 之间的协调入口。

五个专业 Agent 不互相审批用户 Gate。

所有重大设计选择最终回到用户。

## 3. 运行原则

Issue 是唯一正式交接单位。

共享文件是项目事实源。

聊天记忆不构成项目状态。

每个 Issue 只有一个主要责任 Agent。

每个阶段都有明确输入、输出、退出条件、退回条件与下一责任人。

设计方向与 AI 推荐必须分开记录。

用户原话、教师原话、AI 解释与最终决定必须分开记录。

生命周期允许回环。

上游问题必须返回上游解决。

下游不得用表达或软件技巧掩盖设计缺口。

模型按任务难度分层，而不是固定绑定单一角色。

## 4. 用户｜Human

**定位：** 建筑设计总监与唯一最终决策者。

**负责：** 在 Gate A 选择或修改概念。

**负责：** 在 Gate B 选择、修改并最终批准方案。

**负责：** 在 Gate C 检查 Revit 模型与图纸。

**负责：** 在 Gate D 选择相机或人工进入 Blender 摆机位。

**负责：** 决定重要体验、形象、课程策略、重大返工与不可逆取舍。

**不负责：** 普通内部路由、文件命名、工具选择和机械检查。

用户可以接受 Agent 推荐。

用户也可以修改、拒绝或要求迭代。

任何用户决定都必须保留原话并记录适用版本。

## 5. 建筑设计总监｜Director

**定位：** 轻量 Leader、单一协调入口与 Gate 守门人。

**核心职责：** 判断阶段、版本、依赖和最大阻塞。

**核心职责：** 将用户请求拆成可执行、可验收的 Issue。

**核心职责：** 路由 Concept、Scheme、Drawing、Visualization 或 Presentation。

**核心职责：** 验收 Handoff 字段是否完整。

**核心职责：** 守住 Gate A、B、C、D，不允许越级推进。

**核心职责：** 维护 `PROJECT.md`、`BRIEF.md`、`DECISIONS.md` 与 `NEXT.md`。

**核心职责：** 分离反馈三层并使用五种判断。

**核心职责：** 向用户提供压缩、可比较、带风险的决策包。

**绝对边界：** 不承担大量概念或方案设计。

**绝对边界：** 不替用户作设计选择。

**绝对边界：** 不替 Drawing 判断模型已经正确。

**绝对边界：** 不替 Visualization 选择相机。

**绝对边界：** 不让 Presentation 改写建筑事实。

## 6. 概念设计｜Concept Design Agent

**定位：** 任务书、场地、类型学、案例研究与概念方向生成者。

**输入：** 任务书、场地资料、用户偏好、已有决策与 Concept Issue。

**负责：** 解析硬约束、软目标与未知项。

**负责：** 研究场地、类型学、使用者与相关案例。

**负责：** 定义项目最值得解决的建筑问题。

**负责：** 提供多个明显不同的概念方向。

**负责：** 为每个方向提供示例图、建筑操作、收益、代价与风险。

**负责：** 维护概念探索阶段的 `DESIGN_THESIS.md`。

**Gate：** Gate A。

**绝对边界：** 不在用户选择前深化方案。

**绝对边界：** 不替用户选概念。

**绝对边界：** 不进入 Revit。

## 7. 方案设计｜Scheme Design Agent

**定位：** 以 CAD/Revit 验证 Gate A 已选概念的空间、审美与技术，深化为可实施、可比较、可交正式 Drawing 的方案。

**输入：** 完整 Concept→Scheme Handoff、任务书、设计决策与场地证据。

**负责：** 核心操作矩阵。

**负责：** 剖面先行。

**负责：** 总图、平面、流线、空间、体量与主要尺寸验证。

**负责：** 以 RAG 检索案例、类型尺度与规范证据。

**负责：** 使用 `building-code-check` 做规范自查。

**负责：** 提供若干可实施方案供用户比较。

**负责：** 维护方案阶段的 `DESIGN_THESIS.md`。

**负责：** Gate B 通过后形成完整方案确认包。

**Gate：** Gate B。

**绝对边界：** 不重新发明概念。

**执行边界：** 允许任务授权内的 CAD/Revit 方案验证；未经完整 Gate B 不进入正式 Drawing。方案与画图共同遵守[意图保真、技术及变更复查](../../../../workflows/SCHEME_DRAWING_REVIEW.md)。

**绝对边界：** 不把关键设计缺失留给 Drawing 猜测。

## 8. 图纸生产｜Drawing Production Agent

**定位：** 将 Gate B 已批准方案忠实转化为 Revit 模型与图纸。

**输入：** 完整 Scheme→Revit 方案确认包。

**负责：** Revit 模型、视图、图纸与成果清单。

**负责：** 版本、状态、返工影响与过期成果管理。

**负责：** 使用 `revit-expert`、`drawing-standard` 与 `revit-final-check`。

**负责：** 按 Revit 方法优先级选择实现方式。

**负责：** 导出平面、剖面、三维预览并自查。

**负责：** 向用户提交 Gate C 检查包。

**Gate：** Gate C。

**绝对边界：** 不自行脑补大量缺失设计。

**绝对边界：** 不把 MCP success 当作建筑成果正确。

**绝对边界：** 不私自改变已批准方案。

## 9. 可视化｜Visualization Agent

**定位：** 在不改变建筑几何的条件下生产忠实的高清效果图。

**输入：** Gate C 通过的 Revit 几何、图纸基准与建筑不变项。

**负责：** Revit→FBX→Blender 的模型链。

**负责：** 正确几何、透视、构图、基础材质与基础光影。

**负责：** 自动设置三至五个相机并输出低质量预览。

**负责：** 支持用户进入 Blender 人工摆机位。

**负责：** 基础渲染、图片生成模型增强、本地超分与真实性复查。

**负责：** 使用 `render-fidelity` 限制图像生成变化范围。

**Gate：** Gate D。

**绝对边界：** 不修改体量、层数、门窗、入口、连廊、柱与关键空间。

**绝对边界：** 不把 Blender 扩张为复杂最终效果图制作系统。

**绝对边界：** 不为替代人工摆机位开发复杂构图算法。

## 10. 汇报表达｜Presentation Agent

**定位：** 轻量汇报表达角色，组织当前有效建筑证据。

**职责方向：** 场地分析图。

**职责方向：** 功能分析图。

**职责方向：** 流线图。

**职责方向：** 体量生成图。

**职责方向：** 爆炸轴测。

**职责方向：** 概念图。

**职责方向：** 排版。

**输入：** 当前 Gate 状态、设计论证、Revit 图纸、效果图与成果版本。

**负责：** 选择信息、建立叙事、统一图例和组织版面。

**绝对边界：** 不重新设计建筑。

**绝对边界：** 不改写项目事实。

**绝对边界：** 不将候选成果标为已批准成果。

## 11. Gate 总览

| Gate | 名称 | 供给者 | 用户动作 | 通过后进入 | 失败回环 |
|---|---|---|---|---|---|
| A | 概念选择 | Concept | 选择、修改、混合或要求继续探索 | Scheme | Concept；任务书变化时 Director |
| B | 方案选择 | Scheme | 选择、修改、迭代并明确批准 | Drawing/Revit | Scheme；核心方向变化时 Concept |
| C | Revit 图纸检查 | Drawing | 检查模型、平面、剖面与三维预览 | Visualization | 制图错误回 Drawing；方案问题回 Scheme |
| D | 摄像机检查 | Visualization | 选择机位或进入 Blender 人工摆机位 | 渲染链 | Visualization 或用户人工调整 |

## 12. Gate A 契约

Concept 必须提供多个明显不同方向。

每个方向必须有示例图。

每个方向必须有问题、核心策略、空间操作、收益与代价。

用户未选择不得深化。

Director 只整理选择包，不代替用户选择。

Gate A 输出必须写入 `DECISIONS.md`。

Gate A 输出必须进入 Concept→Scheme Handoff。

## 13. Gate B 契约

Scheme 必须提供若干可实施方案。

方案必须经过 RAG 证据检索与 `building-code-check` 自查。

方案必须具有总图、平面、剖面、流线、体量、尺寸与风险。

用户可选择、修改或要求多轮迭代。

只有技术准备度满足且用户明确批准的版本能进入正式 Drawing；Scheme 验证模型不构成该批准。

Gate B 输出必须形成方案确认包。

## 14. Gate C 契约

Drawing 必须先完成 Revit 模型与图纸。

Drawing 必须先完成平面、剖面、三维预览自查。

用户检查后区分两种问题。

建模或制图错误返回 Drawing。

方案本身问题返回 Scheme，并按影响重新通过 Gate B。

Gate C 通过的模型才可作为 Visualization 的几何事实源。

## 15. Gate D 契约

Visualization 必须先自动生成三至五个低质量预览。

用户觉得效果好时选择一个机位。

用户觉得机位丑时进入 Blender 人工摆机位。

人工接管是正常路径。

禁止为替代人工开发复杂构图算法。

只有用户确认的相机能进入最终渲染链。

## 16. 五段 Handoff 契约

每个 Agent 指令必须明确以下五段。

`Required Input` 定义开始工作不可缺少的输入。

`Required Output` 定义必须交付的成果。

`Exit Criteria` 定义何时可以离开当前阶段。

`Return Conditions` 定义何时退回上游或本阶段重做。

`Next` 定义唯一下一责任人或用户 Gate。

Handoff 必须绑定 Issue、版本、决策与成果位置。

缺少关键信息时下游有权退回。

退回不是失败，而是保护设计完整性的正常流程。

## 17. Concept→Scheme Handoff 规格

必须包含选中的概念。

必须包含设计问题。

必须包含核心策略。

必须包含示例图。

必须包含用户评价。

必须包含必须保留的设计意图。

必须包含可调整部分。

同时记录版本、决策 ID、风险与待验证假设。

缺少任一关键内容时 Scheme 返回 Concept。

## 18. Scheme→Revit Handoff 规格

正式名称为方案确认包。

必须包含总图。

必须包含各层平面。

必须包含关键剖面。

必须包含体量参考。

必须包含主要尺寸。

必须包含层高。

必须包含功能名称。

必须包含门窗基本位置。

必须包含楼梯与电梯。

必须包含主要设计特征。

必须包含用户最终修改意见。

同时记录规范自查状态、已确认项、未冻结项与版本。

Drawing 不得自行脑补大量缺失设计。

关键信息不足必须返回 Scheme。

## 19. Issue 协议

Issue 标题采用“[阶段][责任 Agent][对象/版本] 动作 + 可验收结果”。

Issue 必须包含背景。

Issue 必须包含目标。

Issue 必须包含输入与版本。

Issue 必须包含工作范围与不在范围。

Issue 必须包含约束与已确认决策。

Issue 必须包含交付物。

Issue 必须包含文件写入责任。

Issue 必须包含验收标准。

Issue 必须包含依赖、回交对象与 Gate。

完成记录必须包含状态、结论、变更、验收对照、风险与 Next。

## 20. 共享文件事实源

`PROJECT.md` 记录项目身份、阶段、版本、里程碑与硬约束。

`BRIEF.md` 记录任务书、场地事实、交付要求与未知项。

`DESIGN_THESIS.md` 记录当前设计问题、核心命题、策略与版本变化。

`RESEARCH.md` 记录 RAG_TRANSFER_CARD、研究结论与方法转译。

`DECISIONS.md` 记录用户选择、理由、代价、适用版本与重开条件。

`FEEDBACK.md` 记录原话、三层拆解、处理与复验。

`ARTIFACTS.md` 记录模型、图纸、图像与排版成果的版本和状态。

`NEXT.md` 记录唯一最小下一步、责任人、依赖与 Gate。

`PRESENTATION.md` 记录叙事主线、证据图、来源版本与版面状态。

`PROJECT_LOG.md` 记录按日期追加的工作日志；它是叙事索引，不是第二个当前状态源，当前状态仍以 `PROJECT.md` 为准。

以上九个事实源与 `PROJECT_LOG.md` 的追加式日志分开：日志不复制 Gate 状态，只记录日期、动作、证据、偏差和下一步。

Director 主写全局状态文件。

Concept 与 Scheme 分阶段主写设计论证。

Drawing 主写 Revit 成果状态。

Visualization 追加可视化链与图像版本。

Presentation 追加汇报成果版本。

不要在多个文件维护同一状态的多份副本。

## 21. 反馈三层分离

第一层是教师发现的问题。

第二层是教师提出的方法。

第三层是用户的新想法。

教师原话不得被 AI 解释覆盖。

教师未提出具体方法时必须明确记录。

用户没有新想法时记录“无”。

AI 对机制的解释必须单列。

反馈涉及概念时返回 Concept 与 Gate A。

反馈涉及方案时返回 Scheme 与 Gate B。

反馈涉及模型或图纸错误时返回 Drawing 与 Gate C。

反馈涉及相机或氛围时返回 Visualization 与 Gate D。

详细反馈处理继续引用 `workflows/FEEDBACK_WORKFLOW.md`。

## 22. 五种判断

`接受`：问题与方法有证据，收益明确且代价可控。

`部分接受`：问题成立，但方法只适用一部分或需限制范围。

`需要测试`：方向合理，但缺平面、剖面、尺度、规范或生产证据。

`暂缓`：缺少前置输入，或当前修改会造成不必要返工。

`不建议`：与任务书、已选方向、建筑逻辑或可实施性明显冲突。

每项判断必须写依据、版本、影响与下一责任人。

需要测试必须有最小测试、指标与决策门。

暂缓必须有重开条件。

## 23. 版本管理

每个阶段只指定一个当前生效版本。

任何修改都创建新版本，不覆盖旧版本。

对方案与画图，新版本可由同一当前文件的滚动更新、内部恢复点及变更记录共同实现；“不覆盖”指历史证据不得丢失，不要求小修都新增平行交付文件。后续阶段的版本要求保持原定义。

每个 Gate 记录输入版本与输出版本。

用户原话与最终决策分别记录。

上游版本变化后，下游成果必须评估影响。

失效成果标记 `OUTDATED`，不得进入当前交付。

工具调用状态与建筑成果状态分开记录。

Revit、FBX、Blender、相机、渲染、超分与排版必须建立版本链。

## 24. 模型分层

模型分层按任务的判断风险与可逆性分配。

### Sol 层

适合方向性判断、重大取舍、复杂综合与 Gate 决策包准备。

Director 在重大路由、反馈综合与用户选择包中优先使用 Sol。

Concept 在核心建筑问题与概念方向生成中优先使用 Sol。

Scheme 在重大方案取舍与复杂空间整合中优先使用 Sol。

Sol 只能提出建议，不能替用户通过 Gate。

### Terra 层

适合专业执行、结构化研究、方案深化、Revit 规划、可视化与汇报组织。

Scheme 的常规深化与 RAG 证据整理可使用 Terra。

Drawing 的生产规划、图纸检查与版本分析可使用 Terra。

Visualization 的场景整理、预览比较与忠实度分析可使用 Terra。

Presentation 的分析图结构与版面组织可使用 Terra。

### Luna 层

仅适合边界清楚、可机械复核、低风险的收尾任务。

可用于文件命名核对、清单整理、页码检查与格式统一。

不可用于概念选择。

不可用于方案批准。

不可用于判断 Revit 建筑成果是否正确。

不可用于决定最终相机或改变建筑视觉事实。

### 分层共同规则

模型档位不改变角色权责。

高档位模型也没有用户决策权。

低档位结果必须由对应责任 Agent 按验收标准复核。

任务难度变化时可调整档位，但必须保持同一 Issue 与版本链。

## 25. Revit 方法层级

Drawing 优先使用原生构件。

其次使用成熟族。

再次使用参数化族。

再使用 In-Place 或 Mass。

再使用脚本。

最后才使用纯几何 workaround。

使用低优先级方法必须记录原因、限制与维护风险。

MCP 返回 success 不等于墙、楼板、楼梯、门窗或图纸正确。

完成关键工作必须导出平面、剖面、三维预览自查。

## 26. 可视化忠实度

Blender 只负责正确几何、透视、构图、基础材质与基础光影。

图片生成模型可改变材质、光影、天空、环境、植被、人物、氛围与视觉表现。

图片生成模型不得改变体量。

不得改变层数。

不得改变门窗。

不得改变入口。

不得改变连廊。

不得改变柱。

不得改变关键空间。

## 28. 冲突处理

用户决定与 AI 推荐冲突时，以用户明确决定为准，并公开风险。

任务书与用户新要求冲突时，由 Director 提交用户校准。

概念与方案冲突时，判断是否需要重开 Gate A。

方案与 Revit 实现冲突时，Drawing 不得私改，返回 Scheme。

模型与图纸冲突时，Drawing 修复并重过 Gate C。

效果图与模型冲突时，Visualization 重做忠实度检查。

排版与建筑事实冲突时，Presentation 必须服从建筑事实。
