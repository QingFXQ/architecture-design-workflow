# 模型分工与路由规则

本项目按任务难度路由模型，不把角色永久绑死在一种模型上。角色决定责任边界，模型决定本轮推理、工具使用与文字工作的投入等级。无论使用哪一种模型，**执行器负责全部开发与文件修改**；调度器只负责读取项目状态、派发/串行调度 Issue 与保留运行记录，不能代替执行器编码、改配置、制作设计成果或作出用户 Gate 决定。Codex/OpenClaw 是当前适配器示例，通用定义见 [RUNTIME_ADAPTERS.md](../../../RUNTIME_ADAPTERS.md)。

## 一、模型层级

| 层级 | 实际模型名 | 适合的工作 | 不应承担的工作 |
| --- | --- | --- | --- |
| 高价值推理 | `gpt-5.6-sol` | Skill 编写与审校、案例深解、跨文件矛盾分析、复杂方案/规范风险推理、关键交接与最终审查 | 批量摘录、固定格式转换、无判断价值的反复检查 |
| 日常主力 | `gpt-5.6-terra` | 方案深化、Revit/Blender 接入实现、文档与配置集成、带明确验收标准的 Issue、常规代码审查 | 尚未定义问题的重大设计取舍或最终放行 |
| 机械执行 | `gpt-5.6-luna` | 已定义格式的提取、分类、字段补全、清单核对、结构化摘要、批量生成候选检索词 | 选择概念、解释不完整案例、判断模型/图纸正确性 |
| 其他本机可选模型 | 以 Codex 模型选择器实际显示为准；例如仅在本机可见时的 `gpt-5.3-codex-spark` | 极短、明确的即时编码迭代或低风险草稿 | 任何正式 Gate、无人工复核的批量结论 |

`gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna` 是当前 Codex 适配器的首选命名。其他模型不因文档列举而自动获得可用性：启动前以本机执行器的模型选择器/配置为准；不可见的模型不得写入任务配置。模型能力说明参照 OpenAI 官方 Codex 模型说明：Sol 适合复杂开放问题，Terra 是平衡型工作主力，Luna 适合清楚且可重复的高频任务。换用其他执行器时，按 [RUNTIME_ADAPTERS.md](../../../RUNTIME_ADAPTERS.md) 的三档能力映射，不要求同名模型。

## 二、按项目阶段的默认路由

| 阶段或责任 | 默认模型 | 升级到 Sol 的条件 | 可降到 Luna 的部分 |
| --- | --- | --- | --- |
| Director：阶段判断、Issue、Handoff、Gate 状态 | Terra | 多个版本/反馈相互冲突；需要最终审查 | Issue 字段完整性、版本号和链接核对 |
| Concept：任务书拆解、问题定义、案例方法转译 | Terra | 核心问题难以收敛；高质量案例深解；Gate A 选择包定稿 | 标签整理、来源字段摘录、候选词扩展 |
| Scheme：平剖体量、流线、规范风险、Gate B 包 | Terra | 方案有根本冲突、涉及多条件权衡或最终用户比较包 | 面积表整理、已定方案的图纸清单校验 |
| Drawing：Revit 接入、模型/图纸实施与自检 | Terra | MCP/插件故障根因、复杂自动化实现、Gate C 最终审查 | 图名、编号、导出清单、已定义检查项 |
| Visualization：工具接入、真实几何核对、渲染链 | Terra | `render-fidelity` 例外判断、跨图真实性最终复核 | 文件改名、相机参数汇总、预览清单 |
| Presentation：证据选择、叙事和版面任务 | Terra | 关键汇报逻辑或最终交付复核 | Caption 初稿、图例/编号一致性检查 |
| RAG 入库与维护 | Luna | 低质量资料的证据判定、可迁移方法深解、抽样质检 | YAML 字段提取、去重候选、标签初筛 |

## 三、路由决策规则

1. 先定义“完成是什么”和证据来源，再选模型。任务边界不清、涉及用户不可逆选择、跨阶段矛盾或最终验收，直接用 Sol；边界清楚的实现与深化默认 Terra；规则可枚举且结果可批量抽检，才使用 Luna。
2. Luna 的输出只能是候选、索引或初筛，不能直接写成事实、案例结论、规范结论或 Gate 通过。至少由 Terra 复核；高影响内容再由 Sol 或用户复核。
3. Sol 不是默认的“更认真”。已有明确接口、模板和验收标准的工作优先交 Terra，以避免把高推理预算消耗在机械产出上。
4. 一个 Issue 只保留一个主要责任角色；模型可在同一角色内切换。不要以“多模型并行”制造多个互相竞争的设计结论。
5. 任务涉及 Revit、Blender、脚本、配置或仓库修改时，执行者始终是当前执行器。调度器可创建/派发任务或保存状态，但不得充当开发执行器。

## 四、预算与复核纪律

采用“三段式”而非无限 review 循环：

1. **定义**：Terra（或复杂问题用 Sol）确认输入、范围、完成标准与风险；缺关键输入时退回，不开始猜测。
2. **产出**：由被路由模型完成一个可验收版本；机械子项可先由 Luna 批量准备。
3. **复核**：只按预先写明的验收项检查。普通 Issue 由 Terra 复核；重大 Gate、Skill、案例深解、架构或最终交付由 Sol 复核。

每个 Issue 最多进行 **2 轮“产出—复核—修正”**。第 2 轮仍不通过时，停止重复调用，记录未决项、证据缺口和回退对象，交给 Director 路由或交由用户选择。以下情形不计入两轮：用户补充新事实、Gate 决定改变、或发现上游版本错误后回到上游重新立项。

控制成本的具体做法：复用已通过的项目事实源与 RAG 摘要；一次只审一个版本；把大任务拆为可验证的 Issue；为 Luna 给出固定 schema；只在结论会改变下游工作时升级 Sol。禁止让多个模型对同一文本无目标地“再看看”，也禁止把模型调用成功误写为设计、图纸或工具验证成功。
