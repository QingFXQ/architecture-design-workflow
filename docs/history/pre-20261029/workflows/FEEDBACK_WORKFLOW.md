# 反馈闭环工作流

## 1. 规则

Director 记录原话、路由与版本；专业判断由对应角色完成。Issue 是唯一正式交接单位。当前团队没有独立 Critic、QA、Architect、Researcher、Production 或 Graphic 角色，也不创建旧 Squad。

| 反馈内容 | 唯一责任角色 | 主要证据 |
| --- | --- | --- |
| 任务书、范围、用户选择或版本冲突 | Director | `BRIEF.md` / `DECISIONS.md` |
| 命题、场地关系、体验、概念矛盾 | Concept Design | `DESIGN_THESIS.md` / 概念图 |
| 功能、总图、平剖、流线、体量与技术协调 | Scheme Design | 方案图与模型 |
| Revit、视图、图纸、标注与出图 | Drawing Production | `.rvt` / Sheet / View |
| 相机、光影、材质、渲染忠实度 | Visualization | 相机与渲染文件 |
| 叙事、版式、图文一致性 | Presentation | 图板或演示稿 |

## 2. 处理步骤

1. **记录**：Director 在 `FEEDBACK.md` 原样记录反馈、来源、影响版本和不确定处；不得把解释混成用户原话。
2. **路由**：为一个问题创建一个具备验收条件的 Issue，指向上表的单一责任角色。
3. **诊断与修改**：责任角色说明问题机制、改动的图面/文件、未改变的决策、风险和需要回退的条件；把新版本登记到 `ARTIFACTS.md`。
4. **同角色自检**：用修改前后证据核对是否解决原话所指的问题，不能只宣布“已优化”。必要时返回同一角色继续修改。
5. **用户 Gate**：若反馈改变冻结决策或存在两个成立方向，Director 汇总证据并请求用户选择；未经用户选择不得把方向写为确认。
6. **交接**：写入 `NEXT.md`；下游只接收明确版本、已知风险和所需成果，不接收模糊口头结论。

## 3. 完成条件

反馈仅在以下条件都满足时标为已解决：原话仍可追溯；责任角色和新版本明确；有图面、模型或文字证据说明改动；剩余风险与下游影响已登记；需要用户选择时 Gate 已记录。

## 4. 禁止事项

- 不让可视化或版式掩盖 Concept/Scheme 的设计缺口。
- 不把案例名、渲染效果或“AI 建议”当作修改成立的证据。
- 不要求不存在的角色进行审批或复核。
- 不在一个 Issue 内同时改任务书、概念、方案和图纸而不标版本与回退范围。
